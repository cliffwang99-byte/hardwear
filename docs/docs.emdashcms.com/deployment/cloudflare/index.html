Deploy to Cloudflare

This guide deploys an EmDash site to Cloudflare Workers with D1 for its database and R2 for media. Start with an EmDash Cloudflare template or apply the same configuration to an existing Astro site.

Prerequisites

Section titled “Prerequisites”
  • A Cloudflare account
  • The project dependencies installed
  • Wrangler authenticated with Cloudflare (pnpm wrangler login)

Configure bindings

Section titled “Configure bindings”

The Cloudflare templates include the complete Worker entry point and named D1 and R2 bindings. On the first deploy, Wrangler creates either resource if its configured name does not already exist. Keep the names in wrangler.jsonc; Wrangler reconnects later deploys to the same resources.

Build and deploy

Section titled “Build and deploy”

Build and deploy the site once to let Wrangler provision the named D1 database and R2 bucket. Wrangler uses the local login created by pnpm wrangler login.

With the default auto migration mode, EmDash applies pending core migrations when the deployed Worker receives its first request. The Worker leaves large content migrations to emdash migrate and answers with 503 until they are applied. Use Manage core database migrations when a deployment pipeline must apply migrations before new code receives traffic or when you need to inspect, check, or recover a migration.

Until the setup wizard has been completed, EmDash also applies the schema and structure of a seed file once, on the first request. Sample content from the seed is applied only when an administrator chooses it in the setup wizard. The seed is read at build time from .emdash/seed.json, the path in package.json#emdash.seed, or seed/seed.json — whichever is found first — and inlined into the bundle. If none is present, a built-in default seed is used. Subsequent deploys against an existing database leave its content alone.

To change the schema or content model of a site that is already deployed, see Evolving a Deployed Site.

Scheduled publishing

Section titled “Scheduled publishing”

On Cloudflare, EmDash publishes scheduled entries only from the Worker’s scheduled handler, which Cloudflare calls on the schedule of a Cron Trigger. The deployed Worker needs both of the following:

  • A Cron Trigger in the triggers.crons list of wrangler.jsonc, as shown in Configure bindings.
  • The scheduled handler from @emdash-cms/cloudflare/worker, exported from the Worker entry point that main points to, as shown in Add the Worker entry point.

If either is missing, scheduled entries do not go live. In local development with astro dev, EmDash publishes scheduled entries on a timer, so a schedule that works locally does not confirm the deployed configuration.

Run emdash doctor from the project root to check the Cron Trigger and the scheduled handler in the local project files:

When emdash doctor finds both, the output includes a passing scheduler wiring check. A failed scheduler check describes the problem and prints the fix. The check recognizes the Worker entry point shown on this page and the one-line re-export it prints as a fix, so an entry point written another way can fail the check even when it works.

If no scheduler check appears, emdash doctor found no Wrangler configuration in the current directory, or it found neither the Cron Trigger nor the scheduled handler. On a D1 project, the database check fails because it looks for a local SQLite file (./data.db by default). That failure does not affect the scheduler checks.

Deploy after adding or changing the Cron Trigger or the scheduled handler. Cloudflare can take up to 15 minutes to start running a new or changed Cron Trigger. Once the trigger starts running, EmDash publishes entries whose scheduled time has already passed.

To watch the trigger, run pnpm wrangler tail. Each run prints a line such as "* * * * *" @ 9/29/2026, 10:01:00 AM - Ok. Ok means the run ended without an uncaught error. EmDash catches and logs publishing errors, so Ok does not confirm that entries were published. A run that publishes entries also logs a message such as [scheduled] Published 1 scheduled item(s), and errors from the run appear in the same output.

After deployment, the admin dashboard shows Scheduled publishing needs attention when a scheduled entry is past its scheduled time and no scheduler run has completed in the last five minutes. If the Cron Trigger runs less often than every five minutes, the notice can also appear between runs until the next run publishes the entry.

Place the Worker near D1

Section titled “Place the Worker near D1”

Cloudflare runs a Worker near the visitor by default. EmDash server-rendered requests make several D1 round trips, so use Targeted Placement to run the Worker near the D1 primary and make those requests faster.

Wrangler accepts placement.mode: "targeted" with exactly one selector: region, host, or hostname. Select the value that targets the D1 primary location, and add the resulting placement object to wrangler.jsonc. Do not enable D1 read replicas with Targeted Placement. Without replicas, every query uses the nearby primary, including with session: "auto" and coalesce: true.

Workers Cache

Section titled “Workers Cache”

Cloudflare’s Workers Cache puts an edge cache in front of your Worker: matching requests are served without running your Worker at all.

Enable it

Section titled “Enable it”

Use Astro’s Cloudflare cache provider so route rules and Astro.cache set cache headers and the provider can invalidate entries when content changes.

The @astrojs/cloudflare adapter detects cacheCloudflare() and enables Workers Cache in the generated deployment configuration.

EmDash invalidates cached entries automatically when content changes (see Route Caching for the tag convention). You only need to purge yourself for custom tags, for example a manual “clear everything” switch, using the platform’s purge API from your Worker. It needs no Cloudflare REST credentials.

Public pages control their own caching through routeRules and Astro.cache. Keep route rules to your public routes: a rest parameter at the site root, such as /[...slug], also matches the admin and API routes under /_emdash/.

Two things to know before enabling it:

  1. A response with any cache hint is cacheable, even without a route rule. The adapter marks responses that no route rule or Astro.cache.set() call made cacheable as no-store. A hint with tags but no maxAge, such as the site settings and menu hints a layout sets on every page, produces Cloudflare-CDN-Cache-Control: public without a lifetime, so Workers Cache falls back to its default cache lifetimes (2 hours for a 200 response). Give every public route a rule, and keep session-dependent routes free of cache hints.
  2. Cached pages are shared with logged-in editors. The cache runs before your Worker, so it cannot bypass based on request cookies. With the default server-rendered toolbar, a logged-in editor may receive the cached anonymous variant of a public page, without the visual editing toolbar, until the entry expires. Set toolbar: "client" to keep the toolbar reliable on cached pages. Pages rendered for a signed-in user are never stored in the route cache.

For a deeper guide covering route rules, cache tags, EmDash’s built-in invalidation on publish, and the responses that must stay out of the cache, see Route Caching.

Workers Caching is separate from the object cache (objectCache: kvCache({ binding: "CACHE" })), which caches database query results in KV under the Worker.

Custom domains

Section titled “Custom domains”

The first deployment receives a workers.dev URL. The custom domain must already be an active domain managed by Cloudflare in the same account as the Worker. After the Worker responds successfully at its workers.dev URL, add the production domain as a Wrangler route:

Deploy again and verify both addresses. Keeping the workers.dev address available while testing DNS helps distinguish a routing problem from an application problem. To make the new domain the address in sitemaps and search metadata, and in emails and plugins when siteUrl, EMDASH_SITE_URL, or SITE_URL is not set, use Change domain in Settings > General; see Move to a New Domain.

Without siteUrl, EMDASH_SITE_URL, or SITE_URL, setup records the address it runs on as the site’s origin, and passkeys created during setup only work on that address. Run setup on the production domain, or set EMDASH_SITE_URL to it before setup. Setting EMDASH_SITE_URL to another domain after setup moves sign-in to that domain, and passkeys created on the old address stop working there.

Public R2 access

Section titled “Public R2 access”

By default, media is served through EmDash’s authenticated media route. If the bucket has a public custom domain, set that origin as publicUrl so generated media URLs use it:

Public bucket access applies to every reachable object, not only media. Automatic JSON backups use the backups/ prefix in the same storage backend, so do not expose that prefix through the public domain. Choose media storage explains the safe boundary.

Image transformation

Section titled “Image transformation”

EmDash resizes and re-encodes R2 media inside the Worker, through Cloudflare’s IMAGES binding. The Image component from emdash/ui and images in rich text both render through the image endpoint EmDash installs under the Cloudflare adapter. For media on the internal /_emdash/api/media/file/… route, that endpoint reads the source bytes straight from the R2 binding, without an HTTP fetch. Those transforms keep working behind Cloudflare Access and with global_fetch_strictly_public. Media served from a bucket URL — see Public R2 Access — takes the adapter’s own transform endpoint instead, which fetches the file over HTTP before transforming it.

You do not have to declare the binding. @astrojs/cloudflare adds it to the Worker config it generates during astro build, the same way it adds cache for Workers Caching. It does so whenever the runtime image service is cloudflare-binding: imageService unset, the string itself, or { runtime: "cloudflare-binding" }. Every other value — "passthrough", "compile", "cloudflare", "custom" — leaves the binding out. Listing it in your own wrangler.jsonc keeps the intent obvious:

To see what a deploy actually gets, read the generated config rather than wrangler.jsonc. A build writes .wrangler/deploy/config.json, which points wrangler deploy at the merged file (dist/server/wrangler.json by default). Look for an images entry there.

Caution

What a missing binding looks like depends on the media URL. On the internal route the endpoint serves the original file unchanged: pages still render and nothing is logged, but every image is the full-size original rather than a variant scaled to the space it occupies. From a bucket URL the request fails with a 500 instead, because the adapter’s transform endpoint calls the binding without a fallback. imageService: "passthrough" is the deliberate way out — EmDash then leaves the adapter’s passthrough endpoint in place rather than wrapping it.

Cloudflare bills these transforms as Images transformations. Each unique combination of source image and parameters is billed once per calendar month, and repeat requests within that month are free. If a site has 500 source images and requests one thumbnail size and one hero size for every image, those two parameter sets count as 1,000 transformed images for that month. The Images Free plan covers 5,000 unique transformations per month. Past that limit, cached transformations are still served, but new ones return a 9422 error and the image request fails.

Email

Section titled “Email”

Production Workers have no default email delivery service. Magic-link sign-in returns Email is not configured until an email plugin is active.

The Cloudflare email plugin uses a send_email binding. First onboard and verify the sender domain with Cloudflare Email Sending. Cloudflare rejects messages whose From address is not an accepted sender.

Add the binding and register the provider:

The plugin is active from its first deployment. Settings → Email shows the selected provider and can send a test email. Sending fails until the sender is accepted and the binding exists.

The plugin uses the binding named EMAIL unless its binding option names another one. If it is the only active email provider, EmDash selects it automatically. If more than one provider is active, choose the Cloudflare provider under Settings → Email. The optional replyTo address receives replies without changing the accepted From address. A plugin can set replyTo on an individual message, which overrides this option for that message.

Worker secrets

Section titled “Worker secrets”

Store secret values with pnpm wrangler secret put <NAME>. Do not put them in wrangler.jsonc or read them from build-time import.meta.env values.

EMDASH_ENCRYPTION_KEY encrypts plugin settings declared as secrets. Set it before saving a plugin secret, and preserve it separately from D1 backups. During rotation, provide the new key first and retain older keys after commas until every plugin secret has been saved again. Secrets and key management describes rotation and recovery.

The plugin bridge reads this Worker secret binding directly. The generated admin settings route reads it through process.env. With nodejs_compat, Cloudflare populates process.env by default for compatibility dates on or after 2025-04-01. Projects pinned to an earlier date must also add nodejs_compat_populate_process_env before saving encrypted settings.

EmDash reads its secrets from process.env at runtime. Worker code reads bindings from env, imported from cloudflare:workers. Never read secrets through import.meta.env: Vite replaces those values at build time and can write them into the server bundle.

The preview HMAC secret and commenter-IP salt are generated and stored in the database unless you provide runtime overrides. Secrets and key management lists the exact variables, storage locations, and rotation effects.

Preview deployments

Section titled “Preview deployments”

A preview can run as a Worker Preview, which gives each branch its own URL on the production Worker, or as a separate Worker in a named Wrangler environment. Either way, the preview needs a database and bucket separate from production. Never point a preview binding at a production database or bucket.

Worker Previews

Section titled “Worker Previews”

Worker Previews require Wrangler 4.135.0 or later in the project’s dependencies. Projects created from an older EmDash template may pin an earlier version; upgrade it with pnpm add -D wrangler@latest. Previews do not inherit bindings or vars from the top-level configuration; list every binding the preview uses in a previews block.

The Astro Cloudflare adapter adds a SESSION KV binding. wrangler deploy provisions it automatically, but wrangler preview rejects it without a namespace ID. Create the preview resources, including a KV namespace for sessions:

Add the resource identifiers that Wrangler prints to wrangler.jsonc:

Repeat send_email, AI Search, vars, and other bindings when the preview uses those features.

The setup wizard and passkeys need the site URL of the preview. Without siteUrl or EMDASH_SITE_URL, setup fails with SITE_URL_REQUIRED. Pass the preview URL, https://<preview-name>-<worker-name>.<subdomain>.workers.dev, on every preview deployment:

Use the same preview name in --name and in the URL. A siteUrl in astro.config.mjs overrides EMDASH_SITE_URL and is built into every preview, so passkeys on the preview are bound to the production domain and neither setup nor sign-in works there. Set the production URL with EMDASH_SITE_URL in the top-level vars instead.

If the Worker sets workers_dev to false, previews have no URL until you set "preview_urls": true at the top level of wrangler.jsonc and run wrangler deploy once. wrangler preview does not apply this setting. wrangler deploy publishes the code in your current checkout to production, not only the setting, so commit the change and deploy from a clean checkout of your production branch. Then return to your branch and run wrangler preview again.

Set a secret for one preview with pnpm wrangler preview secret put <NAME> --name my-branch. pnpm wrangler preview base-config secret put <NAME> sets a secret for previews created afterwards; existing previews keep their secrets.

Keep these differences from production in mind:

  • Previews share the resources in the previews block. wrangler preview reads the previews block of the branch it deploys, so every branch that keeps the base branch’s configuration uses the same database. The first request to a preview applies pending core migrations, so a branch that upgrades EmDash also migrates the database the other previews use. To isolate a branch, create another D1 database and change database_name and database_id in that branch’s previews block before deploying it.
  • An empty preview database shows the setup wizard. Preview URLs are public, and the first visitor to finish the wizard becomes the administrator. Finish setup immediately after creating the preview, or protect preview URLs with Cloudflare Access.
  • Cron Triggers do not run. Scheduled posts are not published, and plugin cron tasks and scheduled backups do not run on a preview.
  • Passkeys work only on the hostname that registered them. Production passkeys do not work on a preview, and the administrator created on the first preview can sign in with a passkey only on that preview URL. On another preview that shares the database, sign in with a magic link, which needs an email provider and its binding in the previews block, and add a passkey there. Alternatively, isolate the branch with its own database as described above and run setup on it.

Verify the deployment

Section titled “Verify the deployment”
